### A-3. 401 자동 갱신 ⭐ Blocker 5 수정 확인

콘솔에서 스위치를 켜고 **홈이나 아동 관리로 이동**하면 됩니다(`/api/children`을 부르는 화면).

- [ ] **A-3-1** `localStorage.setItem("childcare.mock.force401", "1")` → 화면 이동
  - **기대**: 로그인 화면으로 튀지 않고 데이터가 정상 표시. Network에 `POST /api/auth/refresh` **1건** + 원 요청 재시도 1건
- [ ] **A-3-2** `localStorage.setItem("childcare.mock.force401", "all")` → 화면 이동
  - **기대**: 갱신도 401 → 로그인 화면으로. `localStorage`에 `childcare.refresh_token`이 남아 있지 않다
- [ ] **A-3-3** 홈처럼 요청이 여러 개 동시에 나가는 화면에서 A-3-1 반복 → **refresh는 1건만** 나간다
  - 여러 건이면: 갱신 프라미스 공유가 깨진 것

> 끝나면 `localStorage.removeItem("childcare.mock.force401")`로 꺼 주세요.

## B. 실 서버 API 계약 — 계정 필요 (제가 대신 실행 가능)

`{{TOKEN}}`은 로그인 응답의 `access_token`입니다.

- [ ] **B-1** 로그인 → 응답 본문에 `access_token`·`refresh_token`·`user` 4종이 온다
- [ ] **B-2** `Authorization: Bearer {{TOKEN}}`으로 `GET /api/auth/me` → 200
- [ ] **B-3** ⭐ **아동 등록** — 이름만 넣고 `POST /api/children` → **201**, 응답의 `enrolled_at`이 **오늘 날짜로 채워져 있다**
  - **이번 수정(Blocker 3)의 핵심 확인 지점입니다.** 400이 나거나 `enrolled_at`이 `null`이면 생성 본문에서 빈 값이 여전히 `null`로 나가는 것 — 목은 이 결함을 가립니다
- [ ] **B-4** 같은 이름으로 한 번 더 등록 → `409 DUPLICATE_CHILD`
- [ ] **B-5** `GET /api/children?status=all` / `?status=withdrawn` → 200 (아직 한 번도 확인 못 한 쿼리)
- [ ] **B-6** `DELETE /api/children/{id}` → 200, `status: "withdrawn"`. 한 번 더 → `409 ALREADY_WITHDRAWN`
- [ ] **B-7** `PATCH /api/children/{id}` `{"status":"enrolled"}` → 200, `withdrawn_at`이 `null`로 지워진다
- [ ] **B-8** `PATCH /api/children/{id}` `{"memo":"수정"}` → 200, **다른 필드가 그대로 유지된다**(부분 수정 규약)
- [ ] **B-9** 교사 토큰으로 `POST /api/children` → `403 FORBIDDEN`
- [ ] **B-10** 교사 토큰으로 `GET /api/users` → `403 FORBIDDEN`
- [ ] **B-11** ⚠️ 교사 토큰으로 `PATCH /api/children/{id}` `{"status":"withdrawn"}` → **403이 나와야 정상**
  - **200이 나오면 서버 구멍입니다.** 명세 EP-041 오류표에 403 행이 없어 백엔드가 막지 않을 가능성이 높습니다. FE는 경로를 좁혀 뒀지만 서버가 최후 방어선이어야 합니다 → 백엔드에 전달 필요
