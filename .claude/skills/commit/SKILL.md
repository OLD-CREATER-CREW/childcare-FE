현재 변경 사항을 커밋하세요.

## 커밋 메시지 형식

**중간 커밋 (개발 진행 중):**

```
<Type>:#<이슈번호> <제목>

<본문>

Refs #<이슈번호>
```

**마지막 커밋 (이슈를 닫는 시점):**

```
<Type>:#<이슈번호> <제목>

<본문>

Closes #<이슈번호>
```

> `Closes`는 GitHub에서 PR 머지 시 이슈를 자동으로 닫는 키워드입니다.
> 중간 커밋에 `Closes`를 사용하면 이슈가 조기에 닫힐 수 있으므로 반드시 구분합니다.

## Type 정의

| Type       | 설명                                 |
| ---------- | ------------------------------------ |
| `Feat`     | 새로운 기능 추가                     |
| `Fix`      | 버그 수정                            |
| `Refactor` | 기능 변경 없는 코드 구조 개선        |
| `Chore`    | 빌드, 설정, 의존성 등 비기능적 변경  |
| `Style`    | 코드 포맷팅, 세미콜론 등 스타일 변경 |
| `Docs`     | 문서 작성 및 수정                    |
| `Test`     | 테스트 추가 및 수정                  |

## 작성 규칙

- 제목: 한국어, 동사형으로 종결 (추가, 적용, 제거, 수정 등)
- 제목 끝에 마침표 붙이지 않음
- 제목과 본문 사이 빈 줄 삽입
- 본문: "무엇을" 그리고 "왜" 변경했는지 설명
- Co-Authored-By 등 Claude 서명 포함하지 않음
- footer는 **필수** (이슈 참조 키워드)
- 중간 커밋은 `Refs #N`, 마지막 커밋은 `Closes #N` 사용

## 절차

### 1단계: 민감 파일 체크

staged 파일 중 아래 패턴 확인:

- `.env*` (`.env.example` 제외)
- `*secret*`, `*token*`, `*.pem`, `*.key`

발견 시 사용자에게 확인 후 진행합니다.

### 2단계: 커밋 단위 검토

`git diff --stat` 분석:

- 변경 파일 10개 이상 또는 변경 라인 500줄 이상이면 분리를 제안합니다.

### 3단계: 이슈 번호 추출

```bash
bash .claude/skills/commit/scripts/get-issue-number.sh
```

추출 실패 시 사용자에게 이슈 번호를 확인합니다.

### 4단계: Type 자동 추천

변경 파일 경로/확장자 분석:

| 파일 패턴                    | 추천 Type             |
| ---------------------------- | --------------------- |
| `*.md`, `.claude/`, `docs/`  | `Docs`                |
| `*.spec.ts`, `*.test.ts`     | `Test`                |
| `*.config.*`, `package.json` | `Chore`               |
| 새 파일 추가 위주            | `Feat`                |
| 기존 파일 수정 위주          | `Fix` 또는 `Refactor` |

### 5단계: 마지막 커밋 여부 확인

footer의 이슈 참조 키워드를 결정합니다:

```
이 커밋이 이슈의 마지막 커밋인가요?
1. 네 → Closes #N (이슈 자동 종료)
2. 아니요 → Refs #N (이슈 참조만)
```

### 6단계: 커밋 메시지 생성 및 확인

변경 내용을 분석하여 커밋 메시지를 제안합니다:

```
📝 커밋 메시지 제안:

Feat:#23 로그인 페이지 구현

SSO SDK 기반 로그인 폼 구현.
MutationObserver로 SDK 스타일 오버라이드 처리.

Refs #23

이 메시지로 커밋할까요? (수정하려면 직접 입력)
```

### 7단계: 히스토리 문서 업데이트 제안

커밋 내용을 바탕으로 문서 업데이트를 제안합니다.

**Fix 타입인 경우 (필수 제안):**

```
🐛 Fix 커밋이 감지되었습니다.
troubleshoot.md에 기록해두면 나중에 참고하기 좋아요.

docs/features/{기능명}/troubleshoot.md 에 기록할까요?
1. 네, 지금 바로 기록 (내용 입력)
2. 나중에 /note 로 직접 기록
3. 건너뛰기
```

**그 외 타입인 경우 (선택 제안):**

```
📝 tech.md에 구현 내용을 간략히 기록할까요?

1. 네, 한 줄만 남기기
2. 건너뛰기
```

"네"를 선택하면 `/note` 커맨드 로직으로 문서에 내용을 추가합니다.
기능명은 `current_branch`에서 자동 추출하고, 추출 실패 시 사용자에게 확인합니다.

### 8단계: 타입 체크 게이트 (강제)

커밋 직전에 반드시 `npm run type-check` 를 실행합니다.

```bash
npm run type-check
```

- **통과 시**: 다음 단계(커밋 실행)로 진행
- **실패 시**: 커밋을 중단하고 에러를 사용자에게 보고합니다. 자동으로 코드를 수정하지 않고, 어떤 파일/라인에서 어떤 타입 에러가 발생했는지 요약 후 사용자 결정을 받습니다.

```
❌ type-check 실패 — 커밋 중단

<에러 요약: 파일:라인 + 핵심 메시지>

수정 방법:
1. 제가 수정 시도
2. 직접 수정 후 다시 커밋
3. 그래도 강행 (권장하지 않음)
```

> ESLint 는 type-aware rule 만 검사하기 때문에 Vue 템플릿의 `@update:model-value` 같은 emit 시그니처 mismatch 를 못 잡습니다. `vue-tsc` 기반 type-check 가 그 빈틈을 메웁니다.

### 9단계: 커밋 실행

사용자 확인 후 커밋을 실행합니다:

```bash
git commit -m "Feat:#23 로그인 페이지 구현

SSO SDK 기반 로그인 폼 구현.

Refs #23"
```

완료 후:

```
✅ 커밋 완료
- 해시: [commit hash]
- 메시지: Feat:#23 로그인 페이지 구현
```

### 10단계: progress.md 커밋 로그 업데이트

커밋 완료 후 `docs/features/{기능명}/progress.md`에 이번 커밋 내용을 append합니다.

기능명은 현재 브랜치에서 추출합니다.

- `feature/23-login-page` → `login-page`
- `fix/45-token-error` → `token-error`
- 추출 실패 시 사용자에게 기능명을 확인합니다.

`progress.md`가 없으면 사용자에게 확인 후 생성하거나 건너뜁니다. 이미 존재하면 파일 끝에 아래 형식으로 추가합니다.

```markdown
### Commit — YYYY-MM-DD HH:mm

- Hash: `<commit hash>`
- Message: `Feat:#23 로그인 페이지 구현`
- Issue: `#23`

**변경 요약**

- {이번 커밋에서 바뀐 핵심 내용}

**결정 로그**

- {이번 커밋에서 확정된 구현 방향, 예외 처리, 구조 선택}

**다음 작업**

- {이어질 작업이 있으면 작성}
```

작성 규칙:

- 단순 파일 변경 목록을 그대로 붙이지 말고, 다음 세션이 맥락을 복구할 수 있는 수준으로 요약합니다.
- “결정 로그”에는 커밋 과정에서 확정된 선택만 남깁니다.
- 결정이 없으면 `- 특이 결정 없음`으로 명시합니다.
- 다음 작업이 없으면 `- 없음`으로 명시합니다.

완료 후:

```
📈 progress.md 업데이트 완료
→ docs/features/{기능명}/progress.md
```
